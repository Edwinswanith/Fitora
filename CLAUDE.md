All commands run from the repo root (npm workspaces).

| Command | Purpose |
|---|---|

| `npm run dev` | Run mobile + server in parallel (`predev` runs `scripts/dev-clean.mjs`) |

| `npm run dev:mobile` | Expo dev server for the native/PWA app (`mobile`) |

| `npx ts-node src/scripts/db-integrity-audit.ts` (from `server/`) | Read-only cross-collection consistency audit against the connected DB (duplicate active relationships, orphaned slot locks, etc. — never writes/repairs) |

| `npm test --workspace mobile` | Mobile Jest suite (Ask Agent / voice-assistant logic, under `mobile/src/lib/__tests__/`) |

Env setup: copy `.env.example` to `.env`, `server/.env`, and `mobile/.env`. Server reads env via [server/src/config/env.ts](server/src/config/env.ts) (`MONGODB_URI`, `PORT`, `CORS_ORIGIN`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL`, `GOOGLE_CLIENT_ID`/`APPLE_CLIENT_ID` — comma-separated client IDs; empty disables that sign-in path). Optional subsystem env (each degrades to a no-op/mock when unset, so local dev works without them): `OBJECT_STORAGE_BUCKET`/`OBJECT_STORAGE_PREFIX`/`GCS_SERVICE_ACCOUNT_JSON` (durable upload storage on Google Cloud Storage; required for any real deployment, see Phase 12 below), `GEMINI_API_KEY`/`GEMINI_MODEL` (Ask Agent intent classification, workout-image and meal-photo vision conversion, tour narration), `FCM_PROJECT_ID`/`FCM_SERVICE_ACCOUNT_JSON` (push delivery), `DEEP_GRAM`/`DEEPGRAM_*` (voice STT/TTS for Ask Agent), `RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET`/`RAZORPAY_WEBHOOK_SECRET` (coach subscription payments), `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET`/`LIVEKIT_URL` (live video sessions), `INTERNAL_SWEEP_SECRET`/`CRON_SECRET` (auth for the notification-sweep cron endpoint). When `MONGODB_URI` is non-local (Atlas or any remote host), the server **refuses to start** unless the JWT/sweep secrets are non-placeholder (`strictSecrets` in env.ts — remote DB implies real data, not just `NODE_ENV=production`). Mobile reads `EXPO_PUBLIC_API_BASE_URL` (defaults to the deployed Cloud Run API), `EXPO_PUBLIC_PAYMENTS_ENABLED` (in-app subscribe/switch/payout UI, off unless `"true"`; while off, athletes join a coach via the coach's link-by-email flow; see [mobile/src/lib/features.ts](mobile/src/lib/features.ts)) and `EXPO_PUBLIC_SITE_URL` (where native builds open `privacy.html`/`support.html`). Server side, `paymentsAvailable()` in `services/paymentProvider.ts` refuses checkouts and webhooks (503 `payments_unavailable`) when a real deployment (`strictSecrets`) has no Razorpay keys, because the mock provider's webhook secret is public.

## Architecture

Monorepo (npm workspaces: `mobile` + `server`), plus a root Next.js shim used only for the Vercel single-domain build (see Deployment):
- [mobile/](mobile/) — Expo (expo-router, React Native) app; also exports to web/PWA. Screens by role under `src/app/{athlete,coach,login}`; shared client code in [mobile/src/lib/](mobile/src/lib/). **Before editing anything under `mobile/`, read [mobile/AGENTS.md](mobile/AGENTS.md) first** — it flags that the installed Expo SDK has changed and to check the versioned docs (currently v56) before writing Expo code; `mobile/CLAUDE.md` just includes that file.
- [server/](server/) — Express + Mongoose API mounted under `/api/*`. Entry: [server/src/index.ts](server/src/index.ts) → [app.ts](server/src/app.ts) (router mounting, security headers, error handler).
- `backend/pages/api/` + root `pages/` (symlinked at build time) + `next.config.js` (generated at build time) — a thin Next.js/Vercel wrapper (`[...path].ts` proxies everything to the Express app, `cron/` hosts the notifications-sweep cron target) that exists only so the API can be served from the same Vercel domain as the exported web build. Don't confuse this with a separate backend — the real API logic is 100% in `server/`.

Note: [AGENTS.md](AGENTS.md) mentions an `apps/` directory as an older/alternate deployment snapshot — it has since been deleted from the repo, so there's nothing there to confuse with the current build anymore.

**Mobile auth transport.** The mobile client stores tokens in **expo-secure-store** and sends the access token as a **`Bearer` header** ([mobile/src/lib/api.ts](mobile/src/lib/api.ts)). The server's [auth middleware](server/src/middleware/auth.ts) accepts bearer headers and legacy cookies. Refresh sessions are per device: `User.refreshTokenHashes` (capped at 5, rotated on refresh, removed per device on logout, reset to one on password change); the legacy single `refreshTokenHash` is accepted once and migrated. Clients share the same `/api/*` contract and the `scp.user` profile cache for role routing.

### Non-negotiable invariant: coach scope

A coach must only ever see data for athletes explicitly assigned to that coach — and specifically, for any per-assignment content a *previous* coach created (workout assignments, meal-plan assignments), a coach who has since inherited that athlete must NOT see it either; scope by `assignedBy`/creator, not just current-athlete-assignment, wherever a route reads historical per-coach content (this exact gap was found and fixed as a real cross-coach data leak during the Phase 11 hardening pass — see `routes/coachWorkout.ts` and `routes/coachMealPlans.ts` for the corrected pattern). Enforcement of the base invariant is **three-layered** and all three must remain intact:

1. **JWT auth** — [server/src/middleware/auth.ts](server/src/middleware/auth.ts) verifies the access token (bearer header or `accessToken` cookie), re-reads the user from Mongo, and sets `req.actor = { userId, role }`.
2. **Scope loader + authz guard** — [server/src/middleware/coachAthleteAccess.ts](server/src/middleware/coachAthleteAccess.ts) `loadScope` populates `req.actor.assignedAthleteIds` (coach, from currently-active `CoachAthleteAssignment` rows) and `athleteProfileId` (athlete). `requireAthleteAccess(param)` loads the target `AthleteProfile` and calls `assertCanAccessAthleteProfile`, which delegates to the role-scope check `assertCanAccessAthlete`. This only proves the athlete is *currently* assigned to the requesting coach — it says nothing about who authored a specific historical row, hence the leak note above.
3. **Route role gate** — [server/src/middleware/role.ts](server/src/middleware/role.ts) `requireRole(...)` runs before scope-sensitive routers.

Pattern used by every coach-scoped router (see [server/src/routes/coach.ts](server/src/routes/coach.ts)):

```ts
router.use(requireAuth, requireRole("coach"), loadScope);
router.get("/athletes/:athleteId/...", requireAthleteAccess("athleteId"), handler);
```

When adding new coach endpoints: never query athlete-scoped collections without first restricting to `req.actor.assignedAthleteIds` (or using `requireAthleteAccess` for single-athlete routes) **and**, for anything with its own creator/owner field (an assignment, a session, a review), also filtering by that field against `req.actor.userId`. The coach router is gated `requireRole("coach")`, so any non-coach actor gets `403 forbidden_role`.

> **No admin, no guardian.** The admin role, the `/api/admin/*` endpoints, and the admin frontend flow were removed by request. The Guardian role was also removed entirely (Phase 1 of the Fitora pivot) — `GuardianAthleteLink`, `routes/guardian.ts`, and every guardian branch in scope/notification code are gone; historical `GuardianAthleteLink` rows, if any survive in a given database from before the removal, are simply never read again. **The platform is coach / athlete only.** Do not reintroduce an `admin` or `guardian` role without an explicit ask. `User.academyId` still exists and tags audit rows, but no longer gates access.
>
> **Academy owner (not admin).** `User.isAcademyOwner` is a *scoped coach capability*, added by explicit request: an owner is a normal `coach` who may additionally create/list other coaches in their own academy via the owner-gated `GET/POST /api/coach/coaches` (see `requireOwner` in [server/src/routes/coach.ts](server/src/routes/coach.ts)). It is **not** a role, has **no** academy-wide data access, and adds **no** `/admin` surface — it only fills the coach-provisioning gap left by removing admin. Don't expand it into a general admin without an explicit ask. Bootstrap the first owner with `npm run create-owner --workspace server` ([server/src/scripts/create-owner.ts](server/src/scripts/create-owner.ts)) — there is no in-app path to create the first coach.
>
> **Athlete self-signup (the one exception).** By explicit request, athletes — and *only* athletes — may self-register via the public `POST /api/auth/register-athlete` ([server/src/routes/auth.ts](server/src/routes/auth.ts)), UI at `/register/athlete`. It creates a `User(role: athlete)` + `AthleteProfile` with **no coach assignment and no academy**, then signs them in. Such an athlete is simply *unassigned*, so they stay invisible to every coach (coach-scope invariant intact) until a coach adds them, or the athlete subscribes to one (see Subscriptions below).
>
> **Google sign-in self-signup.** `POST /api/auth/google` ([server/src/routes/auth.ts](server/src/routes/auth.ts)) verifies the Google ID token server-side (Google `tokeninfo` endpoint → asserts issuer/audience/`email_verified`; audience must be in `env.googleClientIds`). For a **first-time** Google identity it provisions an account per the `requestedRole` from the login screen — `athlete` (default; also creates an `AthleteProfile`) or `coach`. Existing users never change role and disabled accounts are never reactivated. A self-provisioned athlete is still unassigned, so the coach-scope invariant holds. (This expands the password path: password self-signup remains **athlete-only**; do not add password self-signup for other roles.)
>
> **Request to join** (`routes/coachJoinRequests.ts`, `services/coachJoinRequest.ts`, model `CoachJoinRequest`): the in-app way for an unassigned athlete to get a coach while payments are off. The athlete asks a *listed* coach (`POST /api/athlete/coaches/:coachId/join-request`, at most one pending per athlete via a unique partial index); the coach sees only name/sport/message (`GET /api/coach/join-requests`) and accepts or declines (`POST /api/coach/join-requests/:id/accept|decline`, atomic pending-to-decided claim). Accept creates the `CoachAthleteAssignment` (the one-active-coach index is the final guard; a request made stale by another coach is closed, not shown). UI: the panel on `/athlete/coach-profile/[coachId]` and the Client requests card on coach Home.
>
> A coach pulls a self-registered athlete onto their squad via `POST /api/coach/athletes/link` (body `{ email }`) — the counterpart to the account-creating `POST /api/coach/athletes`. It only creates a `CoachAthleteAssignment` (no new account, no password), adopts an academy-less athlete into the coach's academy, and 404s on an unknown/non-athlete email. UI: the "Create new / Link existing" toggle on `/coach/athletes/new`.

### One primary coach at a time (V1 product rule)

An athlete may have at most one **active** `CoachAthleteAssignment` at a time — enforced at the DB layer by a unique-partial index (`{athleteId:1}` where `status:"active"`), not just app-level checks. Ending a relationship (`services/coachRelationship.ts` `endRelationship`) flips `status` to `"ended"` and — if a subscription is linked — cancels it immediately (not the softer `cancelAtPeriodEnd` used for a self-serve cancel, since access is ending right now), and also cancels the athlete's still-open coach-owned content (`services/relationshipCleanup.ts` `cancelOpenCoachContentForRelationship`, Phase 12 — flips still-`scheduled` `WorkoutAssignment` rows to `skipped` and still-`active` `MealPlanAssignment` rows to `cancelled`; historical/completed content is untouched). `switchCoach` (`services/coachRelationship.ts`) does **not** end the current relationship up front — since Phase 12's switch-safety rework, it delegates to `services/subscription.ts` `initiateSwitchIntent`, which creates a `CoachSwitchIntent` row and leaves the current relationship fully active while the new coach's checkout is pending; only a **webhook-verified** payment event (`completeSwitchIntent`) atomically ends the old relationship and activates the new one, so an abandoned/failed switch checkout leaves the athlete exactly where they started. (If the athlete has no current coach at all, `switchCoach` just degrades to a plain `initiateSubscription`.) There was, until Phase 10, no API path to end a relationship at all — a real gap that had to be built as part of that phase, not something pre-existing to reuse.

### Domain model

Roles: `coach | athlete` ([server/src/models/User.ts](server/src/models/User.ts)). Athletes have a separate `AthleteProfile` keyed by `userId` — `athleteId` in every athlete-scoped collection refers to `AthleteProfile._id`, not the `User._id`. Coach→athlete relationships live in `CoachAthleteAssignment` (`status: "active"|"ended"`, `endedAt`/`endedReason`, optional `subscriptionId` linking to `AthleteCoachSubscription`). Daily-card aggregation across `Attendance`, `TrainingSession`, `Wellness`, `Recovery`, `Performance`, `Injury` lives in [server/src/services/dashboard.ts](server/src/services/dashboard.ts) (`buildDailyCardsForAthletes`, `computeReadiness`, `dayRange`). Other athlete-scoped collections: `RpeMonitoring`, `WaterIntake`, `CoachComment`, `AthleteNote`, `Announcement`, `Notification`, `Message`, `WorkoutMedia`, `DeviceToken`, `NotificationPreference`, `NotificationDecision`. Service layer beyond dashboard: [activity.ts](server/src/services/activity.ts), [analytics.ts](server/src/services/analytics.ts), [trends.ts](server/src/services/trends.ts), [achievements.ts](server/src/services/achievements.ts), [messaging.ts](server/src/services/messaging.ts), [media.ts](server/src/services/media.ts)/[avatar.ts](server/src/services/avatar.ts).

> **Direct messaging.** Coach⇄athlete 1:1 threads ([server/src/models/Message.ts](server/src/models/Message.ts)). A thread *is* the pair `(coachId, athleteId)` — no Conversation model. `senderRole` marks the author; a message is unread by its recipient while `readAt` is null. Coach routes live under `/api/coach/athletes/:athleteId/messages` + `/api/coach/messages/{threads,unread-count}` (gated by `requireAthleteAccess`, so assigned-only); athlete routes under `/api/athlete/messages/:coachId` + `/api/athlete/messages/{threads,unread-count}` (each validates the coach is an **active** assignment → `403 coach_not_assigned`). Sending fires a best-effort `type: "message"` notification. Delivery is **client-poll** (no WebSocket/SSE yet) — reads aren't rate-limited, sends are. Logic centralized in [messaging.ts](server/src/services/messaging.ts). Mobile screens live under [mobile/src/app/coach/messages.tsx](mobile/src/app/coach/messages.tsx) and [mobile/src/components/MessageCenter.tsx](mobile/src/components/MessageCenter.tsx).

> **Push notifications.** A rules-driven reminder system, not raw push plumbing: [notificationEligibility.ts](server/src/services/notificationEligibility.ts) `evaluateAndDispatch(candidate, opts)` decides *whether* a notification should fire (dedup → already-completed → user-enabled → category-enabled → active-device-token → quiet-hours → daily-cap/min-interval → presence-suppression → atomic claim → deliver → record), [notificationTemplates.ts](server/src/services/notificationTemplates.ts)/[notificationCopy.ts](server/src/services/notificationCopy.ts) generate copy, [fcmDelivery.ts](server/src/services/fcmDelivery.ts) sends via Firebase (no-op if `FCM_*` env is unset), and every decision — sent or suppressed, with a reason — is recorded to `NotificationDecision` for audit. Category is a strict 6-value enum on `NotificationPreference`/`NotificationDecision` (`reminders|alerts|deadlines|digests|milestones|messages`) — `Notification.type` itself is a free string at the schema level. [lib/notificationTypes.ts](server/src/lib/notificationTypes.ts) is the intended type→category registry (dating to Phase 1), but no call site actually imports from it yet — every live call site still hand-inlines its own literal+category pair. [notificationSweep.ts](server/src/services/notificationSweep.ts) is the batch job that walks eligible users via bespoke per-type candidate-builder blocks (`buildAthleteCandidates`/`buildCoachCandidates` — there's no generic "register a new sweep type" hook, each one is its own block); it's invoked by the `INTERNAL_SWEEP_SECRET`/`CRON_SECRET`-guarded `/api/internal/notifications` route, which Vercel's `crons` config ([vercel.json](vercel.json)) hits on a fixed schedule via `backend/pages/api/cron/`. Phase 11 found that none of the Phase 6–10 subsystems (subscriptions, bookings, reviews) fired any notification; **Phase 12 wired all of them up** (subscriptions, booking, workouts, nutrition, content, reviews now call `evaluateAndDispatch` — see e.g. `services/subscription.ts`), so that gap is closed. The still-open gap from that same audit: the pre-Phase-12 baseline (Phase 1) call sites still hand-inline their literal+category pair instead of importing `lib/notificationTypes.ts`, even though every type added since Phase 2 is consumed correctly.
>
> **Voice / Ask Agent.** Two intent pipelines exist; **only V2 is live.** V2 = [routes/athleteVoiceV2.ts](server/src/routes/athleteVoiceV2.ts) (`POST /api/athlete/voice/interpret-v2`) + [voiceIntentInterpreterV2.ts](server/src/services/voiceIntentInterpreterV2.ts) (Gemini only *classifies* intent and extracts entities) + [voiceIntentPolicy.ts](server/src/services/voiceIntentPolicy.ts) (deterministic, unit-tested: owns missing-field, confirmation, and next-action decisions) + the mobile [lib/voiceAssistant/](mobile/src/lib/voiceAssistant/) module (action mapping/dispatch, answer fetching from real app data, never model-stated). V1 ([voiceIntentInterpreter.ts](server/src/services/voiceIntentInterpreter.ts), `/api/athlete/voice/interpret` in `routes/athlete.ts`) is deprecated and not called by the current mobile client; it stays deployed only for stale installs, so don't extend it. Policy decisions belong in `voiceIntentPolicy.ts`, never in the prompt. [routes/voice.ts](server/src/routes/voice.ts) and [voiceStream.ts](server/src/routes/voiceStream.ts) wrap Deepgram STT/TTS (`DEEP_GRAM`/`DEEPGRAM_*`); mobile has an on-device speech-recognition primary path plus a text fallback, so Deepgram is optional. [routes/tour.ts](server/src/routes/tour.ts) + [tourNarrator.ts](server/src/services/tourNarrator.ts) drive a separate scripted "AI Tour" narration feature — don't conflate the two. [FITORA_VOICE_ASSISTANT_CURRENT_BASELINE.md](FITORA_VOICE_ASSISTANT_CURRENT_BASELINE.md) is a file:line-cited audit of this subsystem.
>
> **Coach-uploaded media.** [routes/avatar.ts](server/src/routes/avatar.ts) (mounted at `/api/me`) handles profile avatars; workout/session photos go through [media.ts](server/src/services/media.ts) and, when `GEMINI_API_KEY` is set, [workoutImageConverter.ts](server/src/services/workoutImageConverter.ts) uses Gemini vision to turn a photographed workout plan into structured rows (mocked when the key is absent). `services/exerciseMedia.ts` is the same local-disk pattern for coach-owned, reusable exercise-demo images/short videos. `services/coachVideo.ts` (Phase 9, see below) is the same pattern again but for full-length content-library videos, with its own, much larger size cap (`MAX_COACH_VIDEO_SIZE_MB`, default 250MB vs the shared 8MB default). **All** uploaded files live outside any statically-served directory — every read is an authenticated, ownership/visibility-checked route (`res.sendFile`, which natively supports HTTP Range requests for video scrubbing), never a static file URL. Every upload (these three, avatars, training-session photos, meal scans) goes through `services/objectStorage.ts`: multer writes a temp file named by a server UUID, the route calls `persistUploadOrRespond(req.file, res)` before writing the DB row, reads use `sendStoredObject(res, key, mime)` (Range-capable on both adapters), deletes use `deleteStoredObject`, and AI converters read via `withLocalObjectCopy`. Never `res.sendFile` or `fs.unlink` an upload directly.

**AI-boundary pattern**, used consistently everywhere an external/AI/vision output could reach the database: schema-constrained generation → defensive parse → sanitize (defense-in-depth, applied regardless of source) → human review/confirm gate → persist. Established in `workoutImageConverter.ts`; replicated for meal-scan (`mealScan.ts`) and the AI-vision-adjacent code. Never skip the human-confirm step.

**External-provider adapter pattern**, used for every third-party integration: an interface + a real fetch/JWT-based adapter (never the vendor's own SDK, to keep the dependency footprint small) + a fully offline mock adapter, resolved by a `getXProvider()` singleton based on whether the relevant env vars are set. `services/paymentProvider.ts` (Razorpay) and `services/videoProvider.ts` (LiveKit) are the two real examples — read either before adding a new provider.

> **Unified workouts (Phase 2).** `WorkoutTemplate` (coach- or athlete-authored, `version` bumps on edit) → `WorkoutAssignment` (snapshots `exercisesSnapshot`+`templateVersionSnapshot` at assign time, so a later template edit never mutates an existing assignment) → `ExerciseProgress` (per-set completion) → optionally links to the pre-existing `TrainingSession`/`RpeMonitoring` via `slot`. `ExerciseMedia` is the coach-owned, reusable exercise-demo image/video, distinct from both `WorkoutMedia` (per-athlete photographed-plan review flow) and `CoachVideo` (Phase 9, standalone content library).

> **Nutrition (Phase 3).** `NutritionTarget` (versioned — `effectiveFrom`/`effectiveTo`, unique-partial index enforcing one current target per athlete) computed deterministically by `services/nutritionEngine.ts` (Mifflin-St Jeor BMR, safety-floored). `PlannedMeal` (planned) vs `Meal`/`MealFood` (actually logged) are deliberately separate — confirming a plan creates a new `Meal`, never mutates the `PlannedMeal`. `MealScan`/`MealScanItem` is the AI-boundary-pattern vision flow for photographed meals; low confidence never auto-populates, always requires human confirm.

> **Coach meal plans (Phase 4).** `MealPlan` (coach-authored, `version` bumps on edit) → `MealPlanAssignment` (snapshots `daysSnapshot`, same versioning discipline as `WorkoutAssignment`) → creates real `PlannedMeal` rows an athlete's Phase-3 endpoints already read. Allergy conflicts are a hard 422 block only for foods explicitly `allergenTags`-tagged; everything else surfaces as a non-blocking warning.

> **Coach marketplace (Phase 5).** `CoachProfile` (bio/specializations/`avgRating`/`reviewCount` — the rating fields sit dormant until Phase 10 writes to them) is lazily created on first `GET /api/coach/profile`, `active: false` by default (never auto-listed). `CoachPricingPlan` is a coach's pricing tiers. `GET /api/marketplace/coaches` is public-to-any-authenticated-user browsing, backed by a single `$facet` aggregation in `services/coachProfile.ts` (`listMarketplaceCoaches`) — note this has its **own** inline row-shaping, separate from `serializePublicCoachProfile` (the single-coach detail serializer); a new profile-level field needs updating in both places.

> **Subscriptions & payments (Phase 6, Razorpay).** `AthleteCoachSubscription` (`pricingPlanSnapshot` copied at subscribe time, so a coach editing pricing later never changes an existing subscriber's terms; unique-partial index enforces one non-terminal subscription per athlete), `Payment` (`providerPaymentId` unique index is the actual webhook-replay guard), `PaymentWebhookEvent` (raw-body-hash idempotency ledger, since Razorpay doesn't guarantee a stable per-delivery event id). Activation — and therefore the `CoachAthleteAssignment` relationship itself — is only ever created from a **verified webhook**, never from checkout alone or any client-asserted "paid" flag. `services/paymentProvider.ts` is the provider adapter (see AI/external-provider pattern above). Feature entitlement (`checkFeatureEntitlement`/`checkSessionBookingEntitlement` in `services/subscription.ts`) gates coach-provided features by plan — but **only** when a relationship actually has a linked subscription; a relationship with none (legacy/free) stays fully unpaywalled. This same "no subscription = unpaywalled" convention is reused by Phase 7's booking entitlement and Phase 9's video-library "subscribers" visibility tier.

> **Availability & booking (Phase 7).** `CoachAvailability` (recurring weekly rules, coach's own IANA timezone) + `CoachAvailabilityException` (one-off day override, unique per coach+date) resolve into bookable slots (`services/coachAvailability.ts`, using `zonedMinuteToUtc`/`minuteOfDayInZone` in `services/timezone.ts` for timezone conversion — no external tz library). `CoachSession` is the booking itself, with an embedded `events[]` audit array instead of a separate collection. **The double-booking guard is the single highest-risk piece of code in this codebase**: a naive "read overlapping sessions, then insert if none overlap, inside a transaction" does NOT actually prevent a race — MongoDB's snapshot-isolated transactions only detect a write conflict when two transactions touch the *same* document, and two concurrent bookings each insert a distinct new `CoachSession`. The real guard is `CoachSessionSlotLock`: booking a session also claims one lock row per 5-minute bucket it (plus buffer) occupies, against a unique `{coachId, bucketStart}` index — see `services/bookingConcurrency.ts`. Falls back to a non-transactional path on a non-replica-set standalone dev mongod (same `isUnsupportedTransactionError` detection as `routes/athleteVoiceV2.ts`); production (Atlas) always supports real transactions. Session action routes (confirm/reschedule/complete/join-token) re-verify the underlying relationship is still `active` before proceeding — `cancel` is deliberately exempt, since cleaning up a stale booking must always stay possible.

> **Live video (Phase 8, LiveKit).** The call UI is a static page, [mobile/public/call.html](mobile/public/call.html) (livekit-client UMD pinned by version + SRI hash from jsDelivr), shipped in the web export and opened by [mobile/src/lib/videoCall.ts](mobile/src/lib/videoCall.ts) in the in-app browser with the join token in the URL **fragment** (never sent to a server). There is no native LiveKit SDK in the app. `videoAvailable()` in `services/videoProvider.ts` makes join-token return 503 `video_unavailable` when a real deployment has no LiveKit keys. Athletes book from `/athlete/book-session` (available-slots → `POST /api/athlete/coaches/:coachId/sessions`); coaches confirm/decline every pending request from the Session Requests card on the coach home. `CoachSession.videoRoomRef` is created **lazily** on the first join-token request, not at booking time. `services/videoProvider.ts` is the provider adapter (hand-signed HS256 JWTs matching LiveKit's `AccessToken`/`VideoGrant` shape, Room Service admin calls are Twirp POSTs — no `livekit-server-sdk` dependency). A join token is only issuable for a `confirmed`/`rescheduled` session, within a window around the scheduled time (10 min before → 15 min after), and only while the relationship is still active.

> **Coach content library (Phase 9).** `CoachVideo` (standalone content, NOT exercise-attached — see the media pattern note above) has a 4-tier `visibility`: `private` (coach-only), `selected_clients` (list membership **and** active relationship), `subscribers` (active relationship, reusing Phase 6's unpaywalled-if-no-subscription convention), `public_preview` (no relationship needed). `services/coachVideo.ts`'s `loadAthleteVideoAccessContext`/`isVideoVisible` re-derive this live on every request — no caching, so access is cut off the instant a relationship ends. `CoachVideoProgress` is a checkpointed (not per-tick) watch-progress upsert, unique per `(videoId, athleteId)`.

> **Coach switching & reviews (Phase 10).** `services/coachRelationship.ts` — see "One primary coach at a time" above. `CoachReview` — one review per relationship (`relationshipId` unique index is the actual guard), **only reviewable once the relationship has ended** (confirmed product decision, not during an active one), edit-in-place only (no delete endpoint, so a review can never be re-created after removal). `CoachProfile.avgRating`/`reviewCount` are recomputed server-side from `CoachReview` on every create/edit (`recomputeCoachRatingAggregate`) — no route ever accepts a client-supplied aggregate.

**Account deletion** (`services/accountDeletion.ts`, invoked from `POST /api/auth/account` in `routes/auth.ts`) must cascade-clean every collection referencing a deleted user's id — this was found broken for all 12 of the Phase 6–10 collections during the Phase 11 audit (fixed; if you add a new collection with an `athleteId`/`coachId` field, add its cleanup here too, or a future account deletion will silently leave orphaned/dangling-reference rows). The same gap was later found for `Meal`/`MealFood`, `MealScan`/`MealScanItem`, `NutritionTarget`, `PlannedMeal`, `Routine`, `CoachSwitchIntent`, `VoiceActionReceipt`, and athletes' training-session/meal-scan photos (all fixed, with `CoachJoinRequest` added alongside); stored files are deleted through `deleteStoredObject`.

> **Phase 12 (product-completion/hardening pass).** A follow-up audit + fix pass after Phase 11, covering: the notification-wiring gap above; the coach-switch safety rework above (`CoachSwitchIntent`); relationship-end cleanup of open bookings/slot-locks/coach-owned content (`services/relationshipCleanup.ts`, `bookingConcurrency.ts`'s `cancelOpenSessionsAndVideoRoomsForRelationship`); `liveSessionsPerCycle` usage metering and `maxSessionsPerDay` on `CoachAvailability`/pricing; a readiness-field naming collision on the daily card (`services/dashboard.ts`); a stale-Razorpay-plan-after-price-edit bug. It also added `services/objectStorage.ts` after finding that on Cloud Run (and Vercel) `UPLOAD_DIR` is ephemeral, so uploads were lost on redeploy, restart or scale-to-zero. **Fixed since:** every upload path now goes through it, and setting `OBJECT_STORAGE_BUCKET` switches to `GcsObjectStorageProvider` (Google Cloud Storage JSON API, no SDK; credentials from `GCS_SERVICE_ACCOUNT_JSON` or the Cloud Run metadata server; serves files uploaded before the switch from local disk if present). Without a bucket it stays on local disk and logs a warning when production-bound, so **a real deployment must set the bucket**. `smoke-test-coach-videos.ts` round-trips an object through whichever adapter is active. `server/src/scripts/db-integrity-audit.ts` (read-only, never writes/repairs — run with `npx ts-node src/scripts/db-integrity-audit.ts` from `server/`) is a Phase 12 addition for catching drift like duplicate active relationships, duplicate non-terminal subscriptions, orphaned session slot locks, and corrupt workout-assignment snapshots directly against a live DB.

### Tests

Jest + ts-jest + `mongodb-memory-server` (no external Mongo needed) for almost everything; one suite (`voice-log-session.test.ts`) and the booking-concurrency suite (`coach-sessions-concurrency.test.ts`) use `MongoMemoryReplSet` instead, specifically to exercise the real multi-document-transaction path (a standalone `MongoMemoryServer` rejects transactions outright). Suites live in [server/tests/](server/tests/), one file per feature area roughly matching the phase it landed in — access control, coach dashboard/onboarding, the athlete workspace, RPE/readiness, analytics/trends/activity, messaging, media, the notification pipeline, workouts, nutrition, marketplace, subscriptions/payments, booking/availability, live video, content library, coach switching/reviews, and `phase11-*`/`phase12-*`/`account-deletion-cascade` sets covering hardening-pass fixes — `env-setup.ts` and `global-teardown.ts` are shared test infra, not suites themselves. Mobile has focused Jest tests for the voice assistant / Ask Agent logic (and a few small helpers) under `mobile/src/lib/__tests__/`.

Every phase's persistence logic is additionally verified against a **real Atlas connection** via one-off `server/src/scripts/smoke-test-*.ts` scripts (self-contained, clean up everything they create) — run with `npx ts-node src/scripts/smoke-test-<name>.ts` from `server/` when `MONGODB_URI` in `.env` points at a real reachable cluster.

## Coding style

TypeScript strict mode throughout. Two-space indentation, double quotes, semicolons, `camelCase` for variables/functions; React components and Mongoose models use `PascalCase`. In mobile code, prefer the `@/` path alias. Route/service/utility files use descriptive local naming rather than a fixed suffix convention.

Mobile UI specifics:
- **Saved data / instant start:** `useAsyncData` (lib/fitoraData.ts) caches screen data in memory *and* on the device per user (AsyncStorage, `fitora.cache.v1:<userId>:<key>`); startup reads the stored session and saved screens locally, then `validateSession()` confirms with the server in the background (only an explicit rejection signs out). The server is always the source of truth: every screen still refetches. Anything that signs a user out must go through `lib/auth.tsx` so `clearDataCache()` runs; data with a `date` field is only reused on that same day.
- **Feedback:** after a server-confirmed save call `celebrate({ title, body?, big? })` from lib/feedback.ts (haptic + toast; `big` for goals); `showError()` for quick actions with no inline error area; `selectionFeedback()` for option picks. Never celebrate optimistically.
- **Dates/times:** use `DateField`/`TimeField` (components/DateTimeField.tsx, `.web.tsx` for web); values are local `YYYY-MM-DD` / `HH:MM` strings (lib/dateTimeValues.ts). Never derive a local day with `toISOString().slice(0, 10)` (that's UTC).
- **Ask Agent button:** hidden while idle on routes listed in lib/askAgentVisibility.ts; add new form/editor/chat screens there.
- **New-user fairness:** progress rates count only days since `profile.createdAt` and stay neutral until there's enough history (lib/progressWindow.ts).
- **Theme (Teal + Coral):** one job per color in `lib/theme.ts`: `primary` teal = things you tap; `progress` teal = rings/bars/charts; `energy` coral = streaks and celebrations only (fills/icons; text uses `energyInk`); `warn`/`bad` = warnings and problems only; `ok` = completed. Water screens keep their own blue for the ring/chart only. Never put `progress`/`energy` colored text on white; every text pairing in theme.ts is >= 4.5:1.
- **Screen layout rule:** every main screen = header, then exactly one `HeroCard` (the single thing to do or know now, one action; `calm` for all-good/info states), then `SectionLabel` groups of quieter `AppCard`s ordered by how often they're needed, rarely used items last. The athlete Today hero is driven by `deriveNextAction` (lib/fitoraData.ts); coach screens compute their own hero (requests, today's session, attention, planning gaps, profile setup).
- **Wording:** buttons use Title Case, text links sentence case. Coach-facing text says "client"; the athlete role is "Athlete" (never "User"); "athletes" is only for people browsing the marketplace. Coach Profile is two tabs: Public Profile (what athletes see) and Settings (account).
- **Inner screens** (anything pushed on top of a tab: check-in, water, booking, editors, notifications, messages...) start with `BackHeader` from `components/fitora.tsx` (round back button, left-aligned title, optional subtitle, text or icon action). Don't hand-roll a back row; `EditorHeader` in `planEditor.tsx` is a thin wrapper over it.
- **Metric colors** (`metricColors` in `lib/theme.ts`): readiness teal, nutrition coral, water blue, training violet. Use them wherever that metric appears (rings via `MetricRing`/`MetricTileRing`, bars, chart lines, icon tiles) and never for anything else. Status (ok/warn/bad) stays separate and is shown only for exceptions, e.g. a coach client row shows no chip when the client is fine.
- `components/ui.tsx` is legacy (login, register, add client); its primitives are restyled to match `fitora.tsx`. Build new screens from `fitora.tsx`.
- **Design system:** [mobile/src/components/fitora.tsx](mobile/src/components/fitora.tsx) (tokens in `mobile/src/lib/theme.ts`) is the current component library. [ui.tsx](mobile/src/components/ui.tsx) is the older library, still imported by a few screens (login, register, notifications, coach messages, coach new-athlete); build new UI on `fitora.tsx`, not `ui.tsx`.
- **Push deep links:** a notification `link` only navigates if its path is in `KNOWN_PUSH_ROUTES` in [mobile/src/app/_layout.tsx](mobile/src/app/_layout.tsx); anything else silently falls back to the dashboard. When a new notification type points at a new screen, add the route there too (this was a real shipped bug for `/coach/messages`).

## Deployment

Two independent deploy paths for the same `server/` code — know which one a task targets:

- **API-only, Google Cloud Run** — [deploy.bat](deploy.bat) builds `server/Dockerfile` and deploys it standalone (service `scp-server`, project `coaching-467814`), reading secrets from `env.server.yaml` (copy `env.server.yaml.example`; never commit the real file). This is what `EXPO_PUBLIC_API_BASE_URL` points mobile builds at by default.
- **Combined web+API, single Vercel domain** — `npm run vercel-build` ([scripts/vercel-build.mjs](scripts/vercel-build.mjs)) exports the Expo app to static web (`mobile/` → `dist/` → root `public/`), copies `legal/*.html`, symlinks root `pages/` → `backend/pages/`, drops in `backend/next.config.vercel.js` as root `next.config.js`, then runs `next build` from the repo root. The exported web build calls same-origin `/api/*`, which `backend/pages/api/[...path].ts` proxies into the Express app (`bodyParser: false` — the raw request stream passes through untouched, which is also what keeps the Phase 6 payment-webhook raw-body signature check working on this deploy path). Vercel dashboard needs `MONGODB_URI`, `MONGODB_DB`, `AUTH_SECRET` at minimum; `vercel.json` also wires the notification-sweep cron here. The Vercel entry calls `connectMongo({ waitForIndexes: false })` ([server/src/db/mongoose.ts](server/src/db/mongoose.ts)) to keep cold starts fast, so after a schema/index-changing deploy run `verify-indexes.ts` against the target DB; Cloud Run and scripts still wait for indexes.

For local API dependencies only, [docker-compose.yml](docker-compose.yml) brings up Mongo + API. Cloud Run/Vercel egress IPs must be allow-listed in MongoDB Atlas.
